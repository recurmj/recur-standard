# RIP-010: Consent State Machine Standard

**Status:** Draft  
**Type:** Standards Track (Core)  
**Author:** Mats Heming Julner (Recur Labs)  
**Created:** 2025-11-19  
**Requires:** RIP-001 (Permissioned Pull Authorizations), RIP-002 (Consent Registry)  

---

## Abstract

RIP-010 defines the **canonical state machine for permissioned-pull Authorizations**.

Where RIP-001 specifies *what* an Authorization is, and RIP-009 proves *where* it can be verified (across independent systems via κ₍c₎), RIP-010 specifies **when** that Authorization is considered active, paused, revoked, expired, or depleted.

The goal of this RIP is to:

- give all implementations a **shared vocabulary of consent states**,  
- define **deterministic transitions** between those states, and  
- make those states **portable across systems** using the same κ₍c₎ invariant defined in RIP-009.

This state machine is the coordination layer between:

- raw signatures (EIP-712 Authorizations), and  
- higher-level economic and settlement behavior (RIP-003/004/008 and beyond).

---

## 1. Motivation

A signed Authorization by itself is binary: it either verifies or it does not.

Real systems, however, need **richer consent semantics**:

- Is this Authorization **currently usable**, or has it been revoked?  
- Has it **expired** by time, or been **depleted** by previous pulls?  
- Is it **temporarily paused** by the grantor?  
- Can other systems rely on the registry’s view as a **single source of truth**?

Without a shared state model, each implementation would invent its own semantics, making it impossible for:

- wallets, custodians, and treasuries to reason about consent,  
- cross-network observers to trust each other’s view of authorization status,  
- economic layers (limits, rate controls, rebalancing) to compose safely.

RIP-010 introduces a **minimal, normative state machine** that any RIP-001/002/009 implementation can adopt.

## 2. Model and Terminology

### 2.1 Authorization identity

RIP-001 defines an Authorization:

- `Auth = (grantor, grantee, token, maxPerPull, validAfter, validBefore, nonce)`

RIP-009 shows that its verification is governed by the invariant pair:

- `κ₍c₎(Auth, executor) = (domainSeparator, structHash(Auth))`

For RIP-010, an Authorization’s **identity** is any of:

- `authHash = keccak256(Authorization)` as defined in RIP-001,  
- the pair `(domainSeparator, structHash(Auth))` (κ₍c₎),  
- or a canonical encoding that deterministically maps to the same value.

Implementations **MUST** use a stable, collision-resistant identifier for each distinct Authorization. All state in the registry is keyed by this identifier.

### 2.2 Consent registry

RIP-002 defines a **Consent Registry** as the component that records and serves state for each Authorization.

For RIP-010, we assume a registry that:

- is addressable (on-chain contract or off-chain service),  
- records a **state** and **cap configuration** for each `authId`,  
- exposes read-only views for external verifiers and executors.

This RIP does **not** prescribe how the registry is implemented (NFTs, mappings, databases) — only the observable semantics.

---

## 3. Canonical States

Each Authorization tracked by a compliant registry **MUST** be in exactly one of the following states:

1. **UNSEEN**  
2. **PENDING** (optional)  
3. **ACTIVE**  
4. **PAUSED**  
5. **REVOKED**  
6. **EXPIRED**  
7. **DEPLETED**

### 3.1 UNSEEN

- No record exists for `authId` in the registry.  
- The registry makes **no claim** about the Authorization.  
- Verification of the signature is still possible (RIP-009), but executors **SHOULD NOT** treat it as usable without registration.

### 3.2 PENDING (optional)

- The registry has observed the Authorization but not yet **activated** it.  
- Typical use: cross-network observers that want a two-step process  
  (`observe → setCap/activate`) to avoid accidental activation.  
- Executors **MUST treat PENDING as non-pullable**.

### 3.3 ACTIVE

- The Authorization is registered, valid, and usable.  
- Conditions:

  - Signature is valid under κ₍c₎ (RIP-009).  
  - Current time ∈ `[validAfter, validBefore)` (if enforced).  
  - The Authorization has **remaining cap** (see Section 4).  
  - It has not been revoked or paused.

- Executors **MAY perform pulls** up to the configured caps.

### 3.4 PAUSED

- The Authorization is temporarily disabled by the grantor (or authorized controller).  
- All pulls **MUST revert or be rejected** while PAUSED, even if signature and caps are otherwise valid.  
- The Authorization **MAY** be returned to ACTIVE by an explicit transition.

### 3.5 REVOKED

- The Authorization is permanently disabled.  
- All future pulls **MUST revert or be rejected**.  
- REVOKED is terminal: there is **no transition back** to ACTIVE or PAUSED.

### 3.6 EXPIRED

- The current time is past `validBefore` (or before `validAfter`, depending on policy).  
- EXPIRED is treated as terminal for executors: they **MUST NOT** pull.  
- Registries **MAY** garbage-collect expired records, but **MUST** treat them as non-usable if queried.

### 3.7 DEPLETED

- The Authorization has **no remaining cap** under the registry’s economic rules  
  (for example, total amount pulled has reached the configured cap).  
- DEPLETED and EXPIRED are distinct:

  - EXPIRED: time window ended.  
  - DEPLETED: value budget exhausted.

- Registries **MAY** allow the grantor to **increase cap** and return the Authorization to ACTIVE (see Section 4.3).

## 4. Cap Semantics

RIP-001 defines `maxPerPull` in the Authorization itself. Registries and executors **MUST** enforce this upper bound.

RIP-010 adds **external caps** that live in the registry and govern cumulative behavior.

### 4.1 Cap parameters

Each Authorization **MAY** have:

- `capTotal` — maximum total amount that can ever be pulled.  
- `capOutstanding` — maximum net outstanding value (for credit-like models).  
- `capPeriod` — optional period caps (per day, per epoch, etc).

This RIP does **not** fix a single cap schema, but requires that:

- the registry’s cap logic is **purely a function** of:

  - registry configuration for `authId`, and  
  - the history of accepted pulls;  

- the result is **deterministic and replayable** (given the same inputs, all compliant systems compute the same remaining cap).

### 4.2 Cap-driven transitions

A registry **MUST** mark an Authorization as DEPLETED when, under its cap rules:

- a pull would cause remaining cap to become `< 0`, or  
- remaining cap is `0` and no further pulls are allowed.

Executors **MUST** check for DEPLETED and **reject** pulls that would violate cap semantics.

### 4.3 Cap reconfiguration

Grantors (or their designated controllers) **MAY**:

- increase or decrease caps while the Authorization is ACTIVE or PAUSED,  
- restore a DEPLETED Authorization to ACTIVE by increasing cap,  
- permanently lock caps by transitioning to REVOKED.

Registries **MUST** emit events (on-chain) or change logs (off-chain) for any cap change so observers can recompute state.

---

## 5. State Transitions

### 5.1 Transition table

The following transitions **MUST** be supported by compliant registries:

- `UNSEEN → PENDING`  
  - Trigger: registry observes valid Authorization (optional).  

- `UNSEEN → ACTIVE`  
  - Trigger: grantor (or controller) explicitly registers Authorization with initial caps.

- `PENDING → ACTIVE`  
  - Trigger: grantor (or controller) confirms and sets caps.

- `ACTIVE → PAUSED`  
  - Trigger: grantor (or controller) issues pause command.

- `PAUSED → ACTIVE`  
  - Trigger: grantor (or controller) resumes.

- `ACTIVE → REVOKED`  
  - Trigger: grantor (or controller) revokes Authorization.

- `PAUSED → REVOKED`  
  - Trigger: grantor (or controller) revokes while paused.

- `ACTIVE → DEPLETED`  
  - Trigger: cap calculation shows remaining cap = 0 after a pull.

- `ACTIVE → EXPIRED`  
  - Trigger: time passes beyond `validBefore` (if enforced by registry).

- `PAUSED → EXPIRED`  
  - Trigger: time passes beyond `validBefore`.

- `DEPLETED → ACTIVE`  
  - Trigger: grantor increases cap in a way that restores positive remaining cap.

- `EXPIRED → REVOKED` (optional)  
  - Trigger: registry or grantor “cleans up” expired authorization.

Any unspecified transition (for example REVOKED → ACTIVE) **MUST be rejected**.

### 5.2 Transition preconditions

Registries **MUST** enforce:

- Signature validity (RIP-001/009) **before** allowing any transition into ACTIVE or PENDING.  
- Authorization identity uniqueness:

  - Two different Authorizations MUST NOT be registered under the same `authId`.  
  - Replays of the same Authorization MAY update caps or state, subject to policy.

## 6. Cross-System Consistency

RIP-009 proves that consent verification is invariant across systems that can reconstruct κ₍c₎.

RIP-010 extends this by requiring that **state interpretations** are also consistent:

- If two registries both implement RIP-010 and use the same:

  - Authorization (same κ₍c₎),  
  - cap configuration, and  
  - history of accepted pulls,

  then they **MUST** agree on the resulting state for that Authorization.

This does **not** require global consensus: it only requires that any observer who reconstructs the same inputs obtains the same state by replaying the state machine.

Cross-network implementations MAY designate a **canonical registry** (e.g., an L1 contract) and treat other registries as **mirrors** that:

- observe events from the canonical registry,  
- reproduce the same state transitions,  
- reject any local action that would diverge from canonical state.

---

## 7. Executor Requirements

Executors (PullSafes, routers, treasury managers, etc.) that claim RIP-010 compliance **MUST**:

1. Verify the Authorization’s signature against κ₍c₎ (RIP-009).  
2. Query a RIP-010-compliant registry for the current state of `authId`.  
3. Enforce:

   - pulls are allowed **only** when state is ACTIVE,  
   - pulls are rejected when state is PAUSED, REVOKED, EXPIRED, or DEPLETED,  
   - cap rules (Section 4) are respected for each pull.

Executors **SHOULD** treat UNSEEN and PENDING as non-usable unless explicitly configured to allow “unregistered” consent.

## 8. Reference Data Model

The following Solidity-style struct and enum illustrate a minimal on-chain implementation.

~~~solidity
pragma solidity ^0.8.0;

enum ConsentState {
    UNSEEN,    // implicit default; no record stored
    PENDING,
    ACTIVE,
    PAUSED,
    REVOKED,
    EXPIRED,
    DEPLETED
}

struct ConsentRecord {
    ConsentState state;
    uint256 capTotal;        // optional
    uint256 capUsed;         // optional
    uint256 capOutstanding;  // optional
    uint64  validAfter;
    uint64  validBefore;
}
~~~

Registries MAY extend this struct with implementation-specific fields (e.g., per-period caps, metadata), but **MUST** preserve the meaning of the base states.

## 9. Reference Registry Interface

The following interface illustrates typical methods for a RIP-010-compliant registry.

~~~solidity
interface IConsentRegistry {
    event AuthorizationRegistered(bytes32 authId, address grantor);
    event AuthorizationStateChanged(bytes32 authId, ConsentState newState);
    event AuthorizationCapChanged(bytes32 authId, uint256 capTotal);
    event PullRecorded(bytes32 authId, uint256 amount);

    function getState(bytes32 authId) external view returns (ConsentState);

    function getRecord(bytes32 authId)
        external
        view
        returns (ConsentRecord memory);

    function registerAuthorization(
        bytes32 authId,
        ConsentRecord calldata initialConfig
    ) external;

    function setState(bytes32 authId, ConsentState newState) external;

    function setCap(bytes32 authId, uint256 newCapTotal) external;

    function recordPull(bytes32 authId, uint256 amount) external;
}
~~~

This interface is illustrative; conforming implementations **MAY** use different function names and types, but **MUST** expose equivalent observable behavior.

---

## 10. Backwards Compatibility

- Registries that already implement a subset of these states (e.g., only ACTIVE/REVOKED) may adopt RIP-010 by mapping their internal flags to the canonical states.  
- Existing Authorizations remain valid; RIP-010 does not change κ₍c₎ or RIP-001.  
- Economic layers (RIP-003/004/008) can integrate by referencing the same `authId` and treating RIP-010 state as the **single source of truth** for consent status.

---

## 11. Summary

RIP-010 defines:

- a **minimal universal state machine** for permissioned-pull Authorizations,  
- a vocabulary of states (UNSEEN, PENDING, ACTIVE, PAUSED, REVOKED, EXPIRED, DEPLETED),  
- deterministic **transition rules** driven by grantor actions, time, and cap usage, and  
- expectations for registries and executors to keep behavior consistent across systems.

Together with:

- RIP-001 (Authorization schema),  
- RIP-002 (Consent Registry), and  
- RIP-009 (cross-network verification via κ₍c₎),

this standard completes the **coordination layer for consent**: a precise, portable description of when a signed Authorization is usable, and how that usability evolves over time.
