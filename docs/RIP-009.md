# RIP-009: Cross-Network Consent Verification Standard

**Status:** Draft  
**Type:** Standards Track (Verification)  
**Author:** Mats Heming Julner (Recur Labs)  
**Created:** 2025-11-18  
**Requires:** RIP-001   


---

## Abstract

This RIP defines the standard for **cross-network verification of signed Authorizations**. It specifies how an independent system B reconstructs the exact EIP-712 digest originally signed for system A, and verifies that signature without requiring custody, trust, or shared consensus.

The core result formalized here is the **Cross-System Consent Universality Theorem**:

> If two independent systems reconstruct the same `(domainSeparator, structHash)` pair, then a signature over  
> `keccak256(0x1901 || domainSeparator || structHash)`  
> remains valid across those systems — regardless of chain, VM, consensus, or execution environment.

This invariant is denoted **κ₍c₎**, the “consent constant”.

---

## 1. Motivation

Digital finance has relied exclusively on **push-based** value movement for fifteen years. Push primitives exhibit three structural limitations:

1. **No retention** — value can always exit instantly.  
2. **No continuity** — flows occur as impulses, not schedules.  
3. **No cross-system coordination** — consent cannot be verified consistently outside its originating chain.

RIP-009 introduces **continuity** by defining the first standard for verifying consent across independent computational environments.

This enables:

- multi-chain Authorization,  
- cross-domain pull flows,  
- chain-to-chain observe-and-verify,  
- consent portability,  
- system-level rebalancing,  
- coordination without shared state or consensus.

Note: RIP-009 standardizes verification only. It does not define how value is pulled, settled, or rebalanced; those behaviors are specified in other RIPs (e.g. RIP-003/004).

## 2. Authorization Object (Canonical Definition)

RIP-009 builds on the Authorization defined in RIP-001.

Implementations of RIP-009 **MUST** use the exact Authorization type and `AUTH_TYPEHASH` from RIP-001. Any change to the schema or field order defines a different authorization type and is not compatible with this standard.

### 2.1 Authorization fields

- `grantor` — address  
- `grantee` — address  
- `token` — address  
- `maxPerPull` — uint256  
- `validAfter` — uint256  
- `validBefore` — uint256  
- `nonce` — bytes32  
- `signature` — bytes

### 2.2 Authorization type hash

~~~
AUTH_TYPEHASH = keccak256(
    "Authorization(address grantor,address grantee,address token,uint256 maxPerPull,uint256 validAfter,uint256 validBefore,bytes32 nonce)"
);
~~~

### 2.3 Struct hash

~~~
structHash = keccak256(
    abi.encode(
        AUTH_TYPEHASH,
        grantor,
        grantee,
        token,
        maxPerPull,
        validAfter,
        validBefore,
        nonce
    )
);
~~~

Cross-network verification requires that `structHash` is computed **identically** in all compliant systems.

## 3. Domain Separator Invariance

Domain separators must be constructed using static, deterministic fields:

~~~
EIP712_DOMAIN_TYPEHASH = keccak256(
    "EIP712Domain(string name,string version,address verifyingContract,uint256 chainId)"
);

domainSeparator = keccak256(
    abi.encode(
        EIP712_DOMAIN_TYPEHASH,
        keccak256(bytes(name)),
        keccak256(bytes(version)),
        verifyingContract,
        chainId
    )
);
~~~

**RIP-009 requirement:**  

Two systems can interoperate under this standard if and only if they produce the **same** `domainSeparator`.

This implies identical:

- `name`  
- `version`  
- `verifyingContract`  
- `chainId` *namespace* (this does not have to be an L1 chain id; see Section 7).

---

## 4. StructHash Consistency

Systems A and B MUST compute the same `structHash` by using:

- identical field order,  
- identical ABI encoding rules,  
- identical `AUTH_TYPEHASH`,  
- identical Authorization schema,  
- no environment-dependent inputs (no block number, state root, etc.).

If:

- `structHash_A == structHash_B`

then the signed Authorization is structurally portable across systems.

---

## 5. Cross-System Consent Universality Theorem

### 5.1 Statement

Let systems A and B be independent computational environments (for example, different chains, VMs, or off-chain verifiers).

Assume both reconstruct the same:

- `domainSeparator = D`, and  
- `structHash = S`.

Define the EIP-712 digest:

~~~
digest = keccak256(0x1901 || D || S)
~~~

Then for any ECDSA signature `σ` over `digest`, we have:

- `Verify_A(digest, σ) == Verify_B(digest, σ)`

where `Verify_X` represents standard secp256k1 ECDSA verification in environment X.

Signature validity is independent of:

- chain identity,  
- consensus rules,  
- virtual machine or runtime,  
- local chain state.

We denote the invariant pair (domainSeparator, structHash) as κ₍c₎, the consent constant.

### 5.2 Proof sketch

1. EIP-712 digest computation uses only hashing (`keccak256`) over explicit byte strings. Hashing is deterministic and environment-independent.  
2. The signature `σ` is defined entirely over `digest`. No other state participates.  
3. If A and B reconstruct the same `digest`, signature verification reduces in both systems to checking:

   - `ecrecover(digest, σ) == grantor`.

4. ECDSA verification over secp256k1 depends only on:

   - the curve parameters,  
   - the message (`digest`),  
   - the signature (`σ`),  
   - the public key (or recovered address).

None of these depend on chain context when `digest` is the same.

Therefore, signature validity is invariant across systems as long as `domainSeparator` and `structHash` are invariant.

## 6. Observe-and-Verify Flow (System B)

Given an Authorization originally signed and used on system A:

1. **Observe**  
   System B receives the Authorization fields:

   - `grantor`, `grantee`, `token`,  
   - `maxPerPull`, `validAfter`, `validBefore`,  
   - `nonce`, `signature`.

2. **Reconstruct structHash**  

   Using the canonical schema and `AUTH_TYPEHASH`:

   ~~~
   structHash = keccak256(
       abi.encode(
           AUTH_TYPEHASH,
           grantor,
           grantee,
           token,
           maxPerPull,
           validAfter,
           validBefore,
           nonce
       )
   );
   ~~~

3. **Rebuild domainSeparator**  

   Using the shared logical domain parameters (`name`, `version`, `verifyingContract`, `chainId` namespace value) exactly as defined by the standard or implementation.

4. **Compute digest**  

   ~~~
   digest = keccak256(
       abi.encodePacked(
           "\x19\x01",
           domainSeparator,
           structHash
       )
   );
   ~~~

5. **Verify signature**  

   Recover signer:

   - `recovered = ecrecover(digest, v, r, s)` from `signature`.

6. **Check consent**  

   - if `recovered == grantor`, then System B concludes that the same Authorization was consented to by the same signer as in system A.

This is **cross-system consent verification**.

---

## 7. Domain Namespace Rules

RIP-009 allows domain separators to use **namespace chainIds**, not necessarily on-chain `block.chainid`.

Example:

- `name = "RecurPullSafe"`  
- `version = "1"`  
- `verifyingContract = 0x1234...` (logical verifier identity)  
- `chainId = 1` (logical namespace id, not L1 mainnet)

All systems that wish to interoperate must use the *same* logical combination of:

- `name`  
- `version`  
- `verifyingContract`  
- `chainId` (as namespace)

This ensures deterministic domainSeparator values across environments.

---

## 8. Security Properties

RIP-009 inherits all EIP-712 guarantees:

- **Replay safety** via `nonce` (when combined with a revocation or tracking registry).  
- **Time bounding** via `validAfter` and `validBefore`.  
- **Domain separation** via `domainSeparator`.  
- **Fork resilience**, since digest does not depend on chain state or block height.  
- **Context independence**, as no chain-specific data appears in the digest.

Additional properties specific to RIP-009:

- **Cross-system revocation:** if a shared registry enforces that an Authorization is valid or revoked, all systems referencing that registry see the same result.  
- **Cross-system replay protection:** replay across systems is impossible unless both intentionally adopt the same domain and registry rules.  
- **Human-anchored consent:** validity ultimately depends on the signer’s private key, not on any particular chain.

## 9. Reference Implementation (Solidity)

Below is a minimal reference verifier contract.

~~~
pragma solidity ^0.8.0;

contract RecurCrossNetworkVerifier {
    bytes32 public constant AUTH_TYPEHASH =
        keccak256(
            "Authorization(address grantor,address grantee,address token,uint256 maxPerPull,uint256 validAfter,uint256 validBefore,bytes32 nonce)"
        );

    bytes32 public immutable DOMAIN_SEPARATOR;

    constructor(
        string memory name,
        string memory version,
        address verifyingContract,
        uint256 chainId
    ) {
        bytes32 EIP712_DOMAIN_TYPEHASH = keccak256(
            "EIP712Domain(string name,string version,address verifyingContract,uint256 chainId)"
        );

        DOMAIN_SEPARATOR = keccak256(
            abi.encode(
                EIP712_DOMAIN_TYPEHASH,
                keccak256(bytes(name)),
                keccak256(bytes(version)),
                verifyingContract,
                chainId
            )
        );
    }

    function digestAuthorization(
        address grantor,
        address grantee,
        address token,
        uint256 maxPerPull,
        uint256 validAfter,
        uint256 validBefore,
        bytes32 nonce
    ) public view returns (bytes32) {
        bytes32 structHash = keccak256(
            abi.encode(
                AUTH_TYPEHASH,
                grantor,
                grantee,
                token,
                maxPerPull,
                validAfter,
                validBefore,
                nonce
            )
        );

        return keccak256(
            abi.encodePacked(
                "\x19\x01",
                DOMAIN_SEPARATOR,
                structHash
            )
        );
    }

    function verify(
        address grantor,
        address grantee,
        address token,
        uint256 maxPerPull,
        uint256 validAfter,
        uint256 validBefore,
        bytes32 nonce,
        bytes memory signature
    ) public view returns (bool) {
        bytes32 digest = digestAuthorization(
            grantor,
            grantee,
            token,
            maxPerPull,
            validAfter,
            validBefore,
            nonce
        );

        (bytes32 r, bytes32 s, uint8 v) = _split(signature);
        address recovered = ecrecover(digest, v, r, s);

        return recovered == grantor;
    }

    function _split(bytes memory sig)
        internal
        pure
        returns (bytes32 r, bytes32 s, uint8 v)
    {
        require(sig.length == 65, "BAD_SIG");
        assembly {
            r := mload(add(sig, 32))
            s := mload(add(sig, 64))
            v := byte(0, mload(add(sig, 96)))
        }
    }
}
~~~

## 10. Canonical Specification Summary

To verify consent across systems:

1. Compute identical `domainSeparator`.  
2. Compute identical `structHash`.  
3. Construct the EIP-712 digest:

   ~~~
   digest = keccak256(0x1901 || domainSeparator || structHash)
   ~~~

4. Verify the signature using standard ECDSA (`ecrecover`).  
5. If the recovered signer equals `grantor`, the Authorization is validly consented to in any environment that computes the same digest.

This invariance of signature validity under matching `(domainSeparator, structHash)` is what we call **κ₍c₎, the consent constant**.

---

## Appendix A — Boundary Conditions

The cross-system consent invariance (κ₍c₎) holds under:

- EVM and non-EVM systems,  
- different chain IDs,  
- different consensus mechanisms (PoS, PoW, off-chain, etc.),  
- different runtimes (EVM, WASM, SVM, zkVM, off-chain),  
- different block histories and global state.

It fails only if:

- `domainSeparator` differs,  
- `structHash` differs,  
- the Authorization object was mutated,  
- the signature is malformed or corrupted,  
- a revocation rule (in a shared registry) invalidates the Authorization.

---

## Appendix B — Failure Modes

Common failure modes include:

1. **Domain mismatch**  
   - Different `name` or `version`.  
   - Different namespace `chainId`.  
   - Different `verifyingContract` identity.

2. **StructHash mismatch**  
   - Incorrect field ordering.  
   - Missing or extra fields.  
   - Incorrect `AUTH_TYPEHASH`.

3. **Digest mismatch**  
   - Incorrect EIP-712 prefix (not using `0x1901`).  
   - Incorrect concatenation of `domainSeparator` and `structHash`.  
   - Non-standard serialization for the domain or struct.

4. **Signature mismatch**  
   - Non-normalized `s` (malleability issues).  
   - Corrupted bytes due to encoding or copy/paste mistakes.  
   - Wrong message digest used for signing or verification.

If all RIP-009 rules are followed, these failure modes are avoided and κ₍c₎ holds.

## Appendix X — Formal Derivation of Cross-System Consent Universality

This appendix gives a more formal derivation of why a signed authorization, constructed in the Recur format, must verify identically in any computational environment that implements the same hash and signature primitives. This is the mathematical basis of cross-system consent invariance (κ₍c₎).

### X.1 Setup and notation

Let an authorization be a typed data object:

- `Auth = (grantor, grantee, token, maxPerPull, validAfter, validBefore, nonce)`

with a fixed EIP-712 type definition `TYPE_AUTH` and ABI-encoded field ordering.

Let the EIP-712 domain separator for a given executor address `executor` be:

- `domainSeparator = keccak256( EIP712Domain_TYPEHASH || name || version || executor || salt )`

where `name`, `version`, and `salt` are fixed constants for the implementation, and no chain-local parameter (for example chainId, block height, or state root) appears in this variant.

Define:

- `structHash(Auth) = keccak256( TYPE_AUTH || encode(Auth) )`  
- `D = keccak256( 0x1901 || domainSeparator || structHash(Auth) )`

Let `sk` be a private key on secp256k1, `pk` its corresponding public key, and let `σ` be an ECDSA signature over message `D` under `sk`.

### X.2 Computational environments

Consider two arbitrary computational environments `S1` and `S2` (for example, two blockchains, a chain and an off-chain verifier, or two distinct VMs). Assume:

1. Both implement the same hash function `keccak256`.  
2. Both implement the same EIP-712 layouts:
   - identical `TYPE_AUTH`,  
   - identical `EIP712Domain_TYPEHASH`,  
   - identical field ordering and encoding rules `encode(·)`.  
3. Both implement ECDSA verification over secp256k1 via an operator:

   - `Verify_Si(D, σ, pk) -> {true, false}`  

   or equivalently:

   - `ecrecover_Si(D, σ) = pk` or `⊥` (invalid).

No assumption is made about consensus, state transition functions, or chain identifiers.

### X.3 Lemma 1 — Determinism of encodings

Because `TYPE_AUTH`, `EIP712Domain_TYPEHASH`, and `encode(·)` are specified identically in both systems, given the same `Auth` and `executor`, the byte strings used as inputs to `keccak256` are identical in `S1` and `S2`.

Formally:

- `encode_S1(Auth) = encode_S2(Auth)`  
- `EIP712Domain_S1(executor) = EIP712Domain_S2(executor)`

Therefore, the concatenated preimages for all `keccak256` invocations coincide in the two systems.

### X.4 Lemma 2 — Digest equality

Because `keccak256` is deterministic and both `S1` and `S2` implement the same function, identical preimages yield identical hashes.

By Lemma 1, the inputs to:

- `domainSeparator`,  
- `structHash(Auth)`, and  
- `D`

are identical in `S1` and `S2`. Therefore:

- `domainSeparator_S1 = domainSeparator_S2`  
- `structHash_S1(Auth) = structHash_S2(Auth)`  
- `D_S1 = D_S2 = D`

Note that this equality holds independently of each system’s chain id, consensus rules, or global state, because those parameters do not appear in the preimages by construction.

### X.5 Lemma 3 — Signature verification consistency

ECDSA verification over secp256k1 depends only on:

- the elliptic curve parameters,  
- the message `D`,  
- the signature `σ`,  
- the public key `pk`.

By assumption, both `S1` and `S2` implement the same curve and the same ECDSA verification algorithm. Since Lemma 2 establishes that `D_S1 = D_S2 = D`, for any fixed `σ` and `pk` we have:

- `Verify_S1(D, σ, pk) == Verify_S2(D, σ, pk)`

Equivalently, in terms of recovery:

- `ecrecover_S1(D, σ) == ecrecover_S2(D, σ)`, which is either `pk` or the null result.

No system-local metadata (chain id, block number, etc.) enters into this computation.

### X.6 Theorem — Cross-System Consent Universality

Define the predicate:

- `Consented(Auth, executor, σ, pk)`

as:

> "`σ` is a valid ECDSA signature by `pk` over the EIP-712 digest `D` constructed from `Auth` and `executor` as specified above."

By Lemma 2, `D` is identical in all systems `Si` that implement the same hash and encoding rules. By Lemma 3, verification of `σ` against `D` and `pk` yields the same Boolean result in all such systems.

Therefore, for any two environments `S1` and `S2` satisfying the assumptions:

- `Consented_S1(Auth, executor, σ, pk)` iff `Consented_S2(Auth, executor, σ, pk)`

In words:

> The truth value of “this authorization was consented to by `pk`” is invariant across all compliant computational environments.

This is exactly the Cross-System Consent Universality property: once an authorization `Auth` and executor `executor` are fixed, and a signature `σ` is produced over the derived digest `D`, the validity of that consent does not depend on any network-local property. It depends only on the shared invariant:

- `κ₍c₎(Auth, executor) = (domainSeparator, structHash(Auth))`

### X.7 Consequence — Independence from chains

Because chain ids and all other chain-local variables can be excluded from the domain separator by design (for example by using a logical namespace id instead of `block.chainid`), no particular chain or consensus system can “own” the consent.

Any environment that:

- can reconstruct `κ₍c₎(Auth, executor)`,  
- can compute `D`, and  
- can verify `σ` on secp256k1,

will reach the same conclusion about whether the Authorization was validly consented to.

Thus:

> Consent, once expressed in this form, is chain-agnostic; only the interpreters (verifiers) are chain-local.
