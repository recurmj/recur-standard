# RIP-009: Cross-System Authorization Verification

**Category:** Standard Track — Core  
**Status:** Draft  
**Author:** Recur Labs  
**Dependencies:** RIP-001, RIP-002, EIP-712  
**Created:** 2025  

---

Formal companion:
[Cross-System Authorization Identity](https://github.com/recurmj/recur-standard/blob/main/docs/cross-system-authorization-identity.md)

---

## 1. Abstract

RIP-009 defines the **verification invariant** for EIP-712–based Authorization objects (from RIP-001) across heterogeneous systems.

It does **not** set replay rules, domain construction, revocation semantics, or trust models.  
It defines one requirement only:

> If two systems derive the same `(domainSeparator, structHash)`,  
> they MUST reach the same verdict when verifying a signature over that pair.

This enables **portable, deterministic authorization verification** across chains, clients, and execution environments.  
RIP-009 is compatible with ERC-7964 and application-specific namespace strategies.

---

## 2. Scope

RIP-009 standardizes only:

- equivalence definition for authorization verification  
- digest computation rules  
- signature equivalence behavior across systems  

RIP-009 does **not** standardize:

- nonce or replay semantics  
- how domains are constructed  
- revocation mechanisms  
- verification registry design  
- smart contract wallet deployment strategy  
- cross-chain trust assumptions  

These are defined by RIP-001, RIP-002, or specific implementations.

---

## 3. Definitions

- **Authorization** — Typed EIP-712 struct defined in RIP-001.  
- **domainSeparator** — EIP-712 domain hash.  
- **structHash** — Keccak-256 hash of the encoded Authorization struct.  
- **digest** —  

  ~~~solidity
  keccak256("\x19\x01" || domainSeparator || structHash)
  ~~~

- **σ** — Signature (ECDSA or EIP-1271).

---

## 4. Formal Invariant

### 4.1 Cross-System Signature Equivalence

Let two systems **A** and **B** compute:

- `DA = domainSeparatorA`  
- `DB = domainSeparatorB`  
- `SA = structHashA`  
- `SB = structHashB`

RIP-009 requires:

> If `DA == DB` and `SA == SB`,  
> then **every valid signature σ must produce the same verification result** in both systems.

Formally:

~~~
verify(DA, SA, σ) == verify(DB, SB, σ)
~~~

Applies to both:

- ECDSA verification  
- EIP-1271 contract-based verification  

RIP-009 does not judge *whether* a signature should be valid — only that equivalence must produce identical outcomes.

---

## 5. Relation to RIP-001 and RIP-002

### RIP-001  
Defines the Authorization struct, signing rules, and pull semantics.  
RIP-009 applies verification equivalence to these structures.

### RIP-002  
Defines revocation, usage tracking, and liveness.  
RIP-009 does **not** define revocation; systems must consult a registry.

---

## 6. Implementation Requirements

### 6.1 Authorization Encoding  
Systems MUST encode the Authorization exactly as defined in RIP-001.

### 6.2 Digest Construction  
Digest MUST be computed as:

~~~solidity
keccak256(
    abi.encodePacked(
        "\x19\x01",
        domainSeparator,
        structHash
    )
);
~~~

### 6.3 Signature Verification  

- **EOA:** strict ECDSA recovery with low-s enforcement  
- **Contract wallet:**  

  ~~~solidity
  IEIP1271(grantor).isValidSignature(digest, signature)
  ~~~

Systems MUST NOT reinterpret or extend signature semantics.

## 7. Implementation Notes  
*(Reviewer feedback integrated; non-normative)*

### 7.1 Domain Namespacing  
RIP-009 does not prescribe domain structure.

Two supported approaches:

1. **Logical global namespaces**  
   - globally unique name (e.g., `"RecurPPO"`)  
   - optional logical chain namespace  
   - verifyingContract included  

2. **ERC-7964-style universal domain semantics**  
   - `chainId = 0` used for account-centric universality  

Both are allowed.

---

### 7.2 Replay Models  
RIP-009 does **not** define replay semantics.

Replay protection comes from:

- per-Authorization nonce (RIP-001)  
- registries tracking usage/revocation (RIP-002)  
- implementer choice:  
  - global nonces  
  - per-chain nonces  
  - single-use signatures  

---

### 7.3 Revocation and Liveness  
Revocation depends entirely on RIP-002.

Systems should check:

~~~solidity
!isRevoked(authHash)
~~~

before accepting an Authorization.  
RIP-009 expresses only cross-system verification, not liveness.

---

### 7.4 EIP-1271 Across Chains  

Since 1271 implementations may differ across chains:

- multi-chain deployments SHOULD use identical 1271 code at identical addresses  
**OR**
- treat contract-wallet verification as chain-local  
  (and avoid reusing the same domain across chains)

---

### 7.5 Version Migration

Changing:

- name  
- version  
- verifyingContract  
- chainId (except under ERC-7964 interpretation)

**MUST** produce a new domainSeparator.

Old signatures remain valid only under the old domain.

---

### 7.6 Relationship to ERC-7964

ERC-7964 defines **one domain-policy strategy** for universal EIP-712 identity.  
RIP-009 defines the **general invariant** governing signature equivalence.

Thus:

- ERC-7964 is compatible with RIP-009  
- ERC-7964 domains satisfy the RIP-009 invariant  
- RIP-009 can be used by non-7964 domain strategies as well

## 8. Reference Algorithm

~~~solidity
function verifyAuthorization(
    Authorization calldata auth,
    bytes32 domainSeparator,
    bytes calldata signature
) external view returns (bool ok) {
    // Compute structHash
    bytes32 structHash = keccak256(abi.encode(
        AUTH_TYPEHASH,
        auth.grantor,
        auth.grantee,
        auth.token,
        auth.maxPerPull,
        auth.validAfter,
        auth.validBefore,
        auth.nonce
    ));

    // Compute digest
    bytes32 digest = keccak256(
        abi.encodePacked("\x19\x01", domainSeparator, structHash)
    );

    // EOA case
    if (auth.grantor.code.length == 0) {
        (bytes32 r, bytes32 s, uint8 v) = split(signature);
        return ecrecover(digest, v, r, s) == auth.grantor;
    }

    // EIP-1271 case
    return IEIP1271(auth.grantor).isValidSignature(digest, signature)
        == 0x1626ba7e;
}
~~~

---

## 9. Security Considerations

- Digest computation MUST be deterministic  
- Replay semantics MUST be defined outside RIP-009  
- Divergent EIP-1271 deployment can break equivalence  
- Domain collisions must be avoided by implementation  
- Revocation MUST be enforced by registry semantics
