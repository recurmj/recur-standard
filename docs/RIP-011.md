# RIP-011: Pull-Secured Account (PSA)  
**Custody Semantics Implied by Authorization Objects**

**Status:** Draft (Standards Track: Custody Primitive)  
**Type:** Core Semantics / Value Container  
**Author:** Mats Heming Julner (Recur Labs)  
**Created:** 2025-11-19  
**Requires:** RIP-100, RIP-001  
**Optional:** RIP-002  

---

## 1. Abstract

This RIP defines the **Pull-Secured Account (PSA)**: a minimal Ethereum value-holding contract whose structure is **implied once authorization exists as explicit machine state**.

A PSA is a **custody container**, not an account abstraction.

It exists to answer one question:

> *Where should value live once execution must obey bounded authorization?*

In a PSA:
- value cannot be unilaterally pushed,
- signatures do not imply custody,
- execution is only possible via permissioned pull (RIP-001),
- authorization objects bound all outbound value movement.

---

## 2. Motivation

### 2.1 Authorization precedes custody

RIP-100 establishes that:
- authorization is explicit machine state,
- independent of execution,
- scoped, time-bounded, and revocable.

RIP-001 establishes that:
- execution must be initiated by the grantee,
- authorization must be checked at execution time.

Under these semantics, traditional push-based custody becomes invalid:

> A value container that can unilaterally push cannot correctly enforce bounded authorization.

RIP-011 formalizes the custody primitive implied by this fact.

---

## 3. Non-Goals

This RIP does **not**:

- replace EOAs,
- mandate migration,
- define wallet UX,
- standardize executors,
- introduce governance or upgradeability,
- prevent all loss or cryptographic failure.

PSAs are **opt-in custody containers**, not universal accounts.

---

## 4. Definition

A **Pull-Secured Account (PSA)** is a contract that:

- holds ETH and ERC-20 balances,
- exposes **no general execution or push interface**,
- has **no owner, admin, or privileged role**,
- releases value **only** via permissioned pull execution (RIP-001),
- enforces Authorization Objects on all outbound transfers.

---

## 5. Required Invariants

A compliant PSA MUST satisfy:

1. **No Unilateral Push**
   - MUST NOT expose arbitrary ETH or token transfer functions.
   - MUST NOT expose generic `execute`, `call`, or delegate interfaces.

2. **No Owner or Admin**
   - MUST NOT contain owner, admin, guardian, or governance roles.
   - MUST NOT permit authority reassignment.

3. **Permissioned Pull Only**
   - MUST release value only when called by an executor enforcing RIP-001.
   - MUST require valid Authorization Objects for all outbound transfers.

4. **Authorization-Bounded Execution**
   - All transfers MUST be bounded by Authorization scope, caps, and validity.

5. **No Upgrade Path**
   - MUST NOT be upgradeable.
   - MUST NOT contain `DELEGATECALL` or proxy logic.

6. **No Approval-Based Custody**
   - MUST NOT rely on ERC-20 allowances.
   - MUST execute transfers directly from the PSA.

---

## 6. Minimal Interface (Illustrative)

A PSA SHOULD expose only a narrow pull surface:
‘
pull(
address tokenOrZero,
address to,
uint256 amount,
bytes authorization,
bytes signature
)
‘
Behavior:
- executor validity is checked (optionally via registry),
- Authorization Object is verified,
- value is transferred directly from the PSA.

Receiving ETH and ERC-20 tokens MUST remain permissionless.

---

## 7. Security Model

PSAs do not promise impossibility of loss.

They guarantee **failure containment**:

| Failure | Outcome |
|------|--------|
| Key compromise | No unilateral drain |
| Phishing | Execution bounded by authorization |
| Automation bug | Damage capped |
| Executor failure | Observable and revocable |

Catastrophic, silent drains are structurally impossible.

---

## 7.1 Cryptographic Failure and Migration

This specification does not claim to prevent loss under complete cryptographic breakage (e.g. ECDSA compromise).

Instead, it guarantees that authority is bounded by explicit authorization state, such that partial or future cryptographic failure does not immediately imply total, silent loss.

PSAs are migration-safe, not cryptographically immortal.

---

## 8. Relationship to RIP-002

A consent registry (RIP-002) MAY be used for:
- executor trust coordination,
- authorization observability,
- revocation signaling.

It is optional and not required for correctness.

---

## 9. Summary

RIP-011 defines the custody primitive implied by:

- Authorization Objects (RIP-100), and
- Permissioned Pull execution (RIP-001).

Once authorization is explicit state, **push-based custody is incomplete**.

PSAs are the minimal structure that closes that gap.
