# RIP-001: The Permissioned-Pull Standard  
**Category:** Standards Track (Core Primitive)  
**Author:** Mats Heming Julner     
**Status:** Draft (canonical post-RIP-000 alignment)  
**Created:** 2025  
**Replaces:** ERC-A / ERC-B split drafts (superseded by unified RIP-001)  
**Depends on:** EIP-712  

---

## Abstract

RIP-001 defines the **Permissioned-Pull Standard**, a durable authorization mechanism that enables safe, scoped, revocable, grantee-initiated transfers of ERC-20 tokens.

A **grantor** signs an off-chain *Authorization object* describing:
- who may pull,
- which token,
- how much per pull,
- when the authorization is valid,
- and a unique nonce for replay protection.

A **grantee** may then call `pull()` *within* those bounds.  
Authorization is durable, revocable, portable across chains, and does **not** require modifications to token contracts.

This RIP unifies the previously separated ERC-A (“Authorization”) and ERC-B (“Pull Executor”) drafts into a single coherent standard.

---

## Motivation

Blockchains today rely on **one-shot authorization**: a signature is consumed once and cannot express durable consent. This makes recurring payments, bounded delegation, cross-domain automation, and safe operational flows unnecessarily brittle.

RIP-001 introduces a minimal, stateless, EIP-712 authorization layer that expresses:
- **revocable** consent,  
- **bounded** execution (per-call caps),  
- **time-limited** authority,  
- **explicit** grantee roles,  
- **portable** semantics across chains,  
- **domain-bound** replay protection.

This is the foundational building block underlying the Recur Consent Layer introduced conceptually in RIP-000.

---

## Relationship to Authorization Objects

RIP-001 defines a financial authorization profile for Authorization Objects, where the permitted action is a bounded pull of value from a grantor to a grantee.

This proposal does not define authorization as a primitive. Instead, it specifies how a particular class of Authorization Objects may be consumed by execution systems to perform value transfer, subject to explicit limits and validity constraints.

For general Authorization Objects, see RIP-100.

## Specification Overview

### The Authorization Object (EIP-712)

The durable consent object is a typed EIP-712 struct:

~~~solidity
Authorization(
    address grantor,
    address grantee,
    address token,
    uint256 maxPerPull,
    uint256 validAfter,
    uint256 validBefore,
    bytes32 nonce
)
~~~

Meaning of fields:

- **grantor** — owner of funds  
- **grantee** — executor allowed to call `pull()`  
- **token** — ERC-20 being pulled  
- **maxPerPull** — maximum per execution (NOT cumulative)  
- **validAfter / validBefore** — time window (half-open)  
- **nonce** — single-use replay protection  

### TYPEHASH (normative)

~~~solidity
keccak256(
"Authorization(address grantor,address grantee,address token,uint256 maxPerPull,uint256 validAfter,uint256 validBefore,bytes32 nonce)"
)
~~~

## Executor Interface (normative)

Executors MUST implement the following interface:

~~~solidity
interface IPullExecutor {
    struct Authorization {
        address grantor;
        address grantee;
        address token;
        uint256 maxPerPull;
        uint256 validAfter;
        uint256 validBefore;
        bytes32 nonce;
    }

    function domainSeparator() external view returns (bytes32);

    function pull(
        uint256 amount,
        Authorization calldata auth,
        bytes calldata signature
    ) external;

    function cancel(bytes32 nonce) external; // grantor-only

    event PullExecuted(
        address indexed grantor,
        address indexed grantee,
        address indexed token,
        uint256 amount,
        bytes32 structHash
    );

    event NonceUsed(address indexed grantor, bytes32 indexed nonce);
    event NonceCanceled(address indexed grantor, bytes32 indexed nonce);

    error BadSignature();
    error WrongGrantee();
    error NotYetValid();
    error Expired();
    error OverCap();
    error NonceAlreadyUsed();
    error Revoked();
    error TransferFailed();
}
~~~

## Execution Rules (normative)

A compliant executor MUST:

1. **Compute structHash**

~~~solidity
structHash = keccak256(abi.encode(
    AUTH_TYPEHASH,
    auth.grantor,
    auth.grantee,
    auth.token,
    auth.maxPerPull,
    auth.validAfter,
    auth.validBefore,
    auth.nonce
));
~~~

2. **Compute digest**

~~~solidity
digest = keccak256(abi.encodePacked(
    "\x19\x01",
    domainSeparator(),
    structHash
));
~~~

3. **Recover signer**  
Signature MUST recover to `auth.grantor`.  
Else **revert BadSignature()**.

4. **Check caller**  
`msg.sender` MUST equal `auth.grantee`.  
Else **revert WrongGrantee()**.

5. **Check time window**  
If `now < validAfter` → **NotYetValid()**  
If `now >= validBefore` → **Expired()**

6. **Enforce amount cap**  
If `amount > auth.maxPerPull` → **OverCap()**

7. **Check nonce state**  
If already used or canceled → **NonceAlreadyUsed() / Revoked()**

8. **Mark nonce used BEFORE external calls**

9. **Execute transfer**

~~~solidity
IERC20(auth.token).transferFrom(auth.grantor, auth.grantee, amount)
~~~

If it fails → **TransferFailed()**

10. **Emit events**

- `NonceUsed`
- `PullExecuted`

---

## Revocation

Grantors MUST be able to invalidate unused nonces at any time.

Two methods are allowed:

### Local revocation (in-executor)

~~~solidity
function cancel(bytes32 nonce) external;
~~~

Only `auth.grantor` may call this.

### Registry-based revocation (optional extension)

Executors MAY read from a global registry for cross-domain or multi-executor coherence.

## Rationale

### Why unify ERC-A and ERC-B?

The community feedback and RIP-000 architectural framing indicate:

- Authorization and execution belong in **one coherent primitive**.  
- Two drafts created unnecessary fragmentation.  
- A single RIP-001 spec is clearer for wallet providers, AA frameworks, and protocol implementers.

### Why per-call caps instead of cumulative budgets?

Cumulative budgets require shared state to be synchronized cross-chain.  
Per-call caps keep RIP-001 **stateless**, **portable**, and **chain-agnostic**.

Higher-layer standards (e.g., RIP-007) can introduce budget semantics where appropriate.

### Why portability matters?

Since the Authorization object contains everything needed to interpret consent, any executor deployed on any chain can validate the same Authorization—bounded only by:

- domainSeparator binding  
- grantor’s revocation state  
- ERC-20 allowance for that executor  

This enables cross-chain automation patterns impossible under one-shot authorization.

---

## Security Considerations

- Nonces MUST be single-use.  
- domainSeparator MUST be stable per-deployment.  
- Signature recovery MUST enforce low-s and valid v-values.  
- Nonce marking MUST occur **before** external calls.  
- Transfer MUST revert on failure, not silently succeed/fail.  
- Windows MUST be strictly enforced.  
- Reentrancy MUST be prevented around token transfers.

RIP-001 does **not** solve MEV, privacy, or sequencing policies — it provides a safe primitive for *authorized motion*.

---

## Backwards Compatibility

- Compatible with all ERC-20s supporting `transferFrom`.  
- Fully compatible with EOAs and EIP-1271 smart contract wallets.  
- Does not modify or extend token logic.  
- No migration needed for existing assets.

## Appendix B — Minimal pull() Pseudocode

~~~solidity
function pull(uint256 amount, Authorization calldata auth, bytes calldata sig) external {
    require(msg.sender == auth.grantee, "WrongGrantee");

    bytes32 structHash = keccak256(abi.encode(
        AUTH_TYPEHASH,
        auth.grantor,
        auth.grantee,
        auth.token,
        auth.maxPerPull,
        auth.validAfter,
        auth.validBefore,
        auth.nonce
    ));

    bytes32 digest = keccak256(abi.encodePacked(
        "\x19\x01",
        domainSeparator(),
        structHash
    ));

    if (recover(digest, sig) != auth.grantor) revert BadSignature();

    if (block.timestamp < auth.validAfter) revert NotYetValid();
    if (block.timestamp >= auth.validBefore) revert Expired();
    if (amount > auth.maxPerPull) revert OverCap();
    if (nonceUsed[auth.grantor][auth.nonce]) revert NonceAlreadyUsed();

    nonceUsed[auth.grantor][auth.nonce] = true;

    if (!IERC20(auth.token).transferFrom(auth.grantor, auth.grantee, amount))
        revert TransferFailed();

    emit NonceUsed(auth.grantor, auth.nonce);
    emit PullExecuted(auth.grantor, auth.grantee, auth.token, amount, structHash);
}
~~~
