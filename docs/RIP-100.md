# RIP-100: Authorization Objects (AO)
**Author:** Mats Heming Julner  
**Status:** Draft  
**Type:** Foundational Primitive

---

## Abstract

This proposal defines **Authorization Objects (AO)**: first-class, time-bounded, revocable authorizations that exist independently of execution.

An Authorization Object represents explicit permission for a class of actions to occur, without prescribing *when*, *how*, or *whether* execution takes place.

This proposal defines **no execution semantics**.

---

## Motivation

Most systems implicitly conflate **authorization** with **execution**. Granting permission often triggers immediate action, continuous polling, or time-based execution. This coupling obscures authority, complicates revocation, and makes permission difficult to reason about as a persistent state.

As a result, many systems rely on:
- One-shot permissions that cannot be inspected or revoked
- Time acting as a de facto authority
- Execution systems that infer intent indirectly

Authorization Objects address this by making permission explicit, inspectable, and independently verifiable.

---

## Definition

An **Authorization Object (AO)** is a signed data object asserting:

> “A grantor permits a grantee to perform an action within a defined scope, subject to explicit validity constraints.”

An Authorization Object MUST include:

- **Grantor**: the entity granting authorization  
- **Grantee**: the entity permitted to act  
- **Scope**: an opaque description of the permitted action  
- **Validity Window**: explicit `validAfter` and `validBefore` bounds  
- **Nonce / Salt**: ensuring uniqueness  
- **Revocation Semantics**:  a defined method for invalidation  

The Authorization Object has a deterministic identity, typically derived as a cryptographic hash of its contents.

---

## Non-Goals

This proposal explicitly does **not** define:

- How or when execution occurs  
- Whether execution occurs at all  
- Asset, value, or transfer semantics  
- Scheduling, automation, or triggering behavior  
- Enforcement mechanisms  

Authorization Objects represent **permission**, not **action**.

---

## Lifecycle

1. **Creation**: The grantor signs an Authorization Object  
2. **Existence**:  The object may be stored, transmitted, or observed  
3. **Evaluation**:  Third parties verify validity at a given time  
4. **Revocation**:  The grantor invalidates the authorization  
5. **Expiration**:  The authorization ceases outside its validity window  

At no point does the Authorization Object itself cause execution.

---

## Profiles

Authorization Objects are intentionally generic.

Domain-specific proposals MAY define **profiles** that interpret the `scope` field according to application-specific rules.

Examples include:
- Financial authorization profiles  
- API access authorization profiles  
- Delegated agent authorization profiles  
- Governance and voting authorization profiles  

Profiles do not modify the Authorization Object primitive.

---

## Relationship to Other Proposals

This proposal defines the foundational authorization primitive.

Other proposals define **execution profiles** or **infrastructure** that consume Authorization Objects without altering their definition.

---

## Rationale

By separating authorization from execution, systems can reason explicitly about *why* an action is allowed without conflating permission with timing or automation.

This enables revocable, inspectable, and composable permission systems across domains.
